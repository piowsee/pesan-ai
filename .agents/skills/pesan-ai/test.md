# Testing Expectations

This file describes repo-level testing expectations. Use it with the `vitest` skill for framework-specific testing patterns and mechanics.

## Default Rule

If you change behavior, add or update tests in the same turn.

For this repo, repository query changes are not "too low level" to test. They should usually get a real database-backed repository test in `tests/repositories`.

Because those repository tests hit the real database, test isolation is mandatory, not optional.

## Test Layers in This Repo

- `tests/api/**`: route-handler tests
  - Mock auth helper and service layer
  - Assert HTTP status, JSend shape, pagination, and role behavior
- `tests/services/**`: service tests
  - Mock repositories and external collaborators
  - Assert orchestration, ownership checks, retries, and `ApiError` behavior
- `tests/repositories/**`: integration tests against the real Prisma database
  - Assert query filters, pagination, transactions, unread counters, idempotent upserts, and persisted side effects

When a change crosses layers, update more than one test layer.

## Important Global Test Context

- `vitest.config.mts` uses `jsdom`, `tests/setup.ts`, and tag metadata.
- `tests/setup.ts` globally mocks:
  - logger
  - encryption
  - `AuthHelper`
  - repositories
  - services
  - event bus
  - selected auth and header modules
- Because of that, repository tests must explicitly `vi.unmock(...)` the repository module under test.
- Service tests usually `vi.unmock(...)` the service under test and keep repositories mocked.
- `tests/setup.ts` also loads `dotenv/config`, so DB-backed repository tests run against the real `DATABASE_URL` available in the environment.

## Repository Test Rules

- Tag repository suites with `{ tags: ['db'] }`.
- Use the real Prisma client from `@/lib/server/prisma`.
- Treat repository tests as isolated integration tests against a shared real database.
- Do not rely on test execution order or on rows created by another test.
- Prefer seeded baseline entities from `tests/seed-data.ts` when the existing WABA, phone, or user is enough.
- Use seeded data mainly as stable read-only baseline context. If you mutate seeded rows, either fully restore them in the same test or prefer creating dedicated test rows instead.
- Create extra rows inside the test when you need precise ownership, pagination, or filter scenarios.
- Generate unique IDs, phone numbers, names, or prefixes for temporary rows so concurrent or repeated runs do not collide with each other.
- Scope cleanup to the data that the current suite created.
- Clean up in foreign-key-safe order:
  - messages
  - conversations
  - phone numbers
  - WABAs
  - webhooks if created by the test
- Call `await prisma.$disconnect()` in `afterAll`.

## Isolation Checklist For Real DB Tests

- Start from a known baseline: use `tests/seed-data.ts` only for stable shared fixtures.
- Create suite-specific rows for anything the test will mutate heavily.
- Prefer `randomUUID()` or a unique numeric suffix for ids, phone numbers, and test names.
- Make assertions against rows created by the current test, not against incidental leftovers.
- Delete everything created by the suite in `afterEach`, even when the main assertion already passed.
- Keep cleanup deterministic and safe for repeated runs.

This repo already uses the right pattern in:

- `tests/repositories/conversation.repository.test.ts`
- `tests/repositories/customer-phone-number.repository.test.ts`
- `tests/repositories/waba.repository.test.ts`

Follow those styles before inventing a new test structure.

## Seed Expectations

- `prisma/seed.ts` creates the baseline admin user, regular user, WABA, webhook, phone number, conversation, and messages.
- `tests/seed-data.ts` is auto-generated by the seed script. Treat it as the source of seeded IDs for DB tests.
- If a seeded record is required, fail with a helpful message telling the user to run `prisma db seed`.

## What To Cover by Default

- Route changes:
  - success status
  - JSend payload shape
  - auth and role behavior
  - pagination parsing when applicable
- Service changes:
  - ownership checks
  - repository calls
  - external API calls
  - `ApiError` branches
  - side effects like event emission or token handling
- Repository changes:
  - actual query filters
  - ordering
  - pagination math
  - transaction side effects
  - idempotency for upserts

## Useful Commands

- Run all tests: `pnpm test`
- Reseed baseline DB data when needed: `pnpm prisma db seed`
- Run one repository suite: `pnpm -s vitest tests/repositories/<file>.test.ts --run`
- Run focused route and service tests: `pnpm -s vitest tests/api/<file>.test.ts tests/services/<file>.test.ts --run`

## Bias for This Repo

- If you change a Prisma query, add or update a repository integration test.
- If you change a route contract, add or update a route test.
- If you change orchestration or ownership rules, add or update a service test.
- Do not stop at mocked unit tests when the behavior being changed lives in the actual query.
